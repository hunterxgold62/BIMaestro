**Arrêt et performance : limite structurelle à rendre visible**

Les créations déclaratives rendent la main entre étapes via Idling (CodexRevitBridge.cs:281–313), ce qui constitue une bonne protection. En revanche revit_run_family_program appelle le moteur synchronement (:533, CodexFamilyProgram.cs:77–95). Un appel natif Revit peut empêcher le traitement du bouton Arrêter.

CodexCreationGuard.cs:49–74 ne peut intervenir que lorsque Revit rend la main ou émet un événement exploitable. La limite de cinq minutes repart à zéro à chaque étape (:89) ; elle n'est ni un plafond global ni une interruption garantie du noyau.

Prévoir un budget global configurable et une estimation de complexité avant exécution. Conserver la session dédiée pour les créations lourdes, superviser sa progression depuis le panneau principal et distinguer « arrêt demandé », « nettoyage », « terminé » et « réponse perdue ». Ne pas déplacer les appels API Revit dans un thread de fond pour contourner cette contrainte.

**Améliorations qui rendraient le produit plus utile**

1. Retourner toutes les erreurs de géométrie indépendantes en une seule validation, avec pièce, axe, bornes calculées, épaisseur et scénario. Le rejet actuel à la première erreur (CodexParametricDesign.cs:249) favorise les corrections une par une. La table ci-dessus doit devenir un cas de régression.
2. Garder une description de référence et appliquer des modifications ciblées. Vérifier que les corrections précédentes sont conservées avant le prochain appel. Comparer explicitement la nouvelle description à celle qui a déjà passé des contrôles.
3. Inspecter les paramètres du gabarit avant de proposer leur portée. CodexParameterBuilder.cs:49–56 ne découvre le conflit Hauteur qu'au moment de MakeInstance. Une étape de préparation doit annoncer les paramètres existants et proposer un nom distinct sans changer silencieusement le besoin utilisateur.
4. Présenter une fiche de résultat : aperçu, dimensions, paramètres réellement réglables, tests effectués, avertissements et actions Ouvrir/Charger. Le panneau affiche aujourd'hui les rapports JSON via Append. Distinguer « fichier enregistré », « géométrie vérifiée » et « comportement paramétrique testé ».
5. Mutualiser les consignes de conception et la politique d'erreurs entre Codex et Claude. Claude reçoit un cadre bien plus court et ses retours de création n'incluent pas les images d'aperçu transmises à Codex (CodexWindow.cs:783–793 contre :1094–1107).
6. Préparer quelques parcours fiables : partir d'une famille existante, modifier des dimensions, créer une table ou un équipement simple, ajouter un connecteur ou une représentation. Donner des exemples dont toutes les options sont couvertes par les tests de livraison.

Les derniers datent du 17 septembre : trois scénarios d'angles passent ; la grille, initialement en échec dans un rapport 3/4, passe dans le rapport suivant 1/1. Cela ne valide pas le build courant sur toutes les versions distribuées. Le banc de compilation natif accepte 2023/2024, tandis que son lanceur accepte aussi 2025 : la couverture doit être rendue cohérente.

Avant diffusion générale : suite UI remise au vert ; scénarios d'échec répété, arrêt/reprise et perte de session testés ; création, modification, sauvegarde, chargement et variations vérifiés dans chaque version Revit officiellement supportée. Inclure un compte non connecté, une CLI absente, un réseau indisponible, un gabarit absent, un changement de document et la fermeture du Revit séparé.

Commencer ensuite par un groupe pilote et mesurer le délai jusqu'au résultat utilisable, les demandes nécessitant plusieurs corrections et les demandes abandonnées. Les critères de réussite doivent porter sur la famille obtenue et son comportement, pas seulement sur l'absence d'exception.
